## Phase 1: データ生成パイプラインの実運用化

**ゴール**: `tools/data_generator.py` を実際にOverpass API / Wikipedia APIに
接続して動かし、数百〜数千件規模の地点データを生成できる状態にする。

> **⚠️ ネットワーク制約(重要)**: この開発サンドボックス環境のプロキシ設定では
> `overpass-api.de` と `ja.wikipedia.org` へのアクセスが403でブロックされる
> (`unpkg.com`がブロックされ、Leafletをvendoringで回避したのと同じ制約)。
> そのため、以下のコード自体は実装・ロジック検証済みだが、**実際の全国データ生成は
> このサンドボックス内では実行できていない**。ネットワーク制限のない環境
> (自分のPC、CI等)で下記コマンドを実行してほしい:
> ```
> python3 tools/data_generator.py --regions kanto --out /tmp/test_kanto   # まず1地方で試す
> python3 tools/validate_data.py --data /tmp/test_kanto                  # 検証
> python3 tools/data_generator.py --regions all --out data                # 問題なければ全地方
> python3 tools/validate_data.py --data data
> ```

> 二回目以降の再実行や地方追加時は既存キャッシュがあれば再取得されない。
>
> **2026-07-30追記**: 駅・接続グラフ(26駅)と経済バランス(Phase3)を保ったまま
> 観光名所だけ実データで増やしたい場合は、上記の代わりに`--places-only`モードを使う
> (docs/HANDOFF.md §13参照)。`stations.json`/`connections.json`には一切手を付けない:
> ```
> python3 tools/data_generator.py --places-only --regions kanto --data data --out /tmp/test_kanto

## Phase 2: 到達可能性判定の本実装(blockReachability.json)【完了】

**ゴール**: §7.4で仮実装した「直線距離の増減」判定を、より正確な判定に置き換える。
Phase 1でデータ規模が拡大すると、直線距離ヒューリスティックの誤判定(分岐点での往復)
が増えるため、優先度は高い。

> **設計変更(実装時の裁量)**: 当初は§3.3のブロック隣接テーブル参照のみを想定していたが、
> 実装・デバッグの過程で「駅グラフは既に完全な接続情報を持っている」ことを踏まえ、
> **目的地からのDijkstra最短距離**を第一優先の判定手段とした。ブロック隣接BFSは、
> 将来地点数が数万件規模になりグラフ全体のDijkstraが重くなった場合の中間フォールバックとして
> 実装・接続済み(現状の規模、駅数十〜数百件では出番はほぼ無い)。直線距離判定は最終フォールバック
> として残している。優先順位: ①グラフ最短距離 → ②ブロック隣接BFS → ③直線距離。
> `isReachableToward(fromNode, toNode, destinationNode, reachability)` のインターフェースは
> 維持しつつ、第4引数で到達可能性コンテキストを渡す形にした。

### タスク
- [x] `data_generator.py` に `--blocks-only` モードを追加し、既存の手動データ

      (ネットワーク不要。以前のプレースホルダーnoteファイルを置き換え)
- [x] `movement.js` に `buildGraphDistances`(目的地からのDijkstra最短距離)と

## Phase 3: バランス調整・ゲームプレイ品質【完了(シミュレーションベース)】

**ゴール**: 「知らない場所を発見する」という核となる面白さが、実際のプレイ感として
成立しているかを検証し、数値を調整する。

> **手法についての注記**: このセッションには人間のプレイテスターがいないため、
> 「社内プレイテスト」の代わりに、実際のゲームロジックをPlaywrightで自動運転する
> シミュレーションハーネスを作り、3種類の疑似プレイヤー方策
> (greedy=候補最上位に従う標準的プレイヤー、discovery=未発見地点を優先する探索型、
> rush=徒歩以外を優先する最短ルート型)で各12〜15回プレイさせ、集計指標
> (手数・距離・所持金推移・空腹喉の最小値・移動手段内訳・イベント発生率)を比較する
> 定量的アプローチを取った。実際の人間によるプレイ感の検証ではないため、
> リリース前に本物のプレイテストを行うことを推奨する。

### タスク
- [x] 発見スコア計算式(§4)を実データ(57ノード: 地点31+交通ノード26)で分析。
      有名観光地(東京駅10点・清水寺10点・姫路城18点)は低スコア、
      無名地点(星野洞80点・宗谷岬78点・佐渡金山65点)は高スコアとなっており、
      意図通りの分布(範囲8〜80、平均33.2)だったため**変更なし**
- [x] 初期所持金・交通費相場のバランス調整:
      シミュレーションで「所持金が一度もタイトにならない」
      (平均最終所持金2300前後・最小値も1800以上で推移)ことが判明。
      **鉄道/フェリーの運賃を旧来比45%、飛行機を50%に一律引き下げ**
      (`data/stations.json`・`data/connections.json`・
      `data_generator.py`のコスト計算式を同時に修正し、将来の実データ生成にも反映)。
      再シミュレーションで平均最終所持金が930〜1140、最小値も1000〜1900で推移するようになり、
      「頻繁に有料交通機関を使うが使い切りはしない」という狙った緊張感に近づいた
      (それでも一度も所持金0には到達しなかった=詰みリスクは低いままで安全)
- [x] ランダムイベント(§7.3)を4種類→8種類に拡充(`js/game.js`)。
      発生確率(25%)はシミュレーションで移動の10〜19%相当の頻度で発生しており
      妥当と判断、**変更なし**
- [x] ヒッチハイク成功率・スコアを全面的に見直し(**重要な発見**):
      シミュレーションで「無料のヒッチハイクが有料交通機関よりほぼ常に高スコアになり、
      鉄道がほとんど選ばれない」問題を発見(評価式が成功率を考慮しておらず、
      失敗コストがスコアに反映されていなかったため)。
      対策: ①ヒッチハイクのprogressスコアに成功率を掛けて期待値化
      (`expectedProgress = progress * successRate`)、②陸上ヒッチハイクの基礎成功率を
      0.85→0.55に引き下げ(フェリーの30%は§7.1.1の明記値のため維持)。
      結果、鉄道利用が全トライアル合計で約13回→21〜36回に増加し、有料交通機関が
      実質的な選択肢として機能するようになった
- [x] 空腹/喉の渇きの減衰率: シミュレーションで最小値が34〜60%程度で推移し、
      食事/水分補給が1ゲームあたり平均0.7〜2.8回発生する程度だったため、
      過度に厳しくはないと判断し**変更なし**
- [ ] プレイ時間の目安(1周30分〜1時間程度)との整合性は**要検証**。
      現行データ(31地点・26ノード)ではgreedy方策で平均15〜16手・discovery方策で
      35〜39手で到着しており、実プレイヤーの意思決定時間を考慮しても現状は
      「30分〜1時間」より短いクイックプレイになっている可能性が高い。
      Phase 1の実データ拡張(地点数百〜数千件)によって手数が自然に増える見込みのため、
      その後に改めてこの項目を検証する

### 2026-07-30セッションでの追加調整: アルバイト3回/ノード上限後のHARD難易度

Phase 5(テスト整備)のシミュレーションで、アルバイトの同一ノード3回上限
導入後、HARD難易度(初期¥3000・ヒッチハイク運-15%)で、遠方かつ運賃の高い
目的地(特にflight-only区間を含む離島行き)に当たると、資金繰りが厳しくなり
到着までの手数が大きく伸びるケースがあることが判明した(詳細は
docs/HANDOFF.md §9.2)。`tools/balance_harness.js`(このセッションで新設)を
使い、以下の手順で定量的に対応した。

- **調査**: greedy方策・2000シードでHARDの到着手数を集計。
  平均36.2手・中央値24手・p99=223手(EASY平均11.4手・NORMAL平均17.3手と比較して
  明らかに裾が重い)。800手以内に0.2%(4/2000)が未到着。
- **試した案と結果**(いずれも2000シードで比較。数値はHARDのみ):
  | 変更 | 平均 | 中央値 | p90 | p99 |
  |---|---|---|---|---|
  | (変更前) | 36.2 | 24 | 80 | 223 |
  | WORK_WAGE 1000→1300のみ | ほぼ変化なし/一部悪化 | - | - | - |
  | HARD初期¥3000→¥4000のみ | **32.2** | **21** | **71** | **185** |
  | 上記+WORK_WAGE→1200 | 32.1 | 20 | 74 | 193(notArrived 4→1) |
- **採用した変更**: **HARDの初期所持金を¥3000→¥4000に引き上げ**
  (`js/game.js`の`DIFFICULTY_PRESETS.hard.initialMoney`)。単独で明確な改善が
  見られ、他の変更(賃金アップ)を重ねてもノイズの範囲でしか変わらなかったため、
  変更点を1つに絞った。`WORK_MAX_PER_NODE`(ユーザー指示による3回上限)自体は
  変更していない。
- **残課題**: 800手以内に到着しないケースが引き続き僅かに残る(0.2%程度)。
  追跡すると、いずれも現行データセット(26交通ノード)で「南大東空港」
  (`stations.json` id=23)が目的地に選ばれたケースだった。この地点は
  `data/stations.json`上で那覇空港(id=19)からのflight接続1本のみで
  他に接続を持たない、現行データセット内で唯一と言っていい「単一の高額
  必須区間」であり、Phase 1で実データ(数百〜数千件規模)に拡張すれば
  代替ルート・周辺の労働機会が増えて自然に緩和されると見込まれる。
  データファイル(`stations.json`)に手動で接続を追加するような対症療法は、
  実在しない交通網を捏造することになるため今回は行っていない。
  再現・定量化には `node tools/balance_harness.js --difficulty hard --seeds 2000` を使う。

### 2026-07-30セッションでの追加調整(同日2回目): ユーザー指示7点

同日中にユーザーから7点の追加指示(観光名所での食事・温泉、既訪問地点の
候補整理、ヒッチハイクの仕様変更3点、駅1つにつき観光名所1つへのデータ整理、
候補の休憩/移動カテゴリ分け、行動不能時のゲームオーバー)があり、全て対応した。
詳細はdocs/HANDOFF.md §12を参照。特筆すべき点:

- ヒッチハイクを「運賃が払えない場合のみ」に制限し、失敗ペナルティを
  固定値から空腹・体力の半減(切り捨て)に強化。観光名所データも31件→24件に
  整理(駅1つにつき1つが基本方針に)。これらにより経済的な制約はさらに
  厳しくなり、`tools/balance_harness.js`での到着/ゲームオーバーまでの
  手数はさらに伸びている(seed=9のようにHARDでは万単位の手数を要する
  極端なケースも残る。tests/regression.test.jsでは専用の緩いテストに切り出し済み)。
- **重要な発見**: 「既に訪れて進行にも寄与しない観光名所を候補から除外する」
  変更を実装した直後、離島の孤立した交通ノード(南大東空港)で実際に
  詰み(候補0件)が発生することをシミュレーションで発見・修正した

```
Phase 1 (データ拡張) ─┬─> Phase 2 (到達可能性本実装) ─> Phase 3 (バランス調整)
                      │                                        │
                      └─> Phase 5 (テスト整備、Phase1と並行可)  │
                                                                 ▼
                              Phase 4 (UI/UX) ──────────> Phase 6 (公開)
                                                                 │
                                                                 ▼
                                                   Phase 7(将来拡張・任意)
```

Phase 1のデータ拡張後は速やかに着手すること。
