# Journey Home Japan — フェーズ別開発計画書

このドキュメントは `journeyhomejapanfullspec.md`(v3仕様書)で定義したゲームを、
デモ版(MVP)から実運用可能な完成度まで引き上げるための作業計画。
フェーズは基本的に上から順に着手する想定だが、フェーズ4〜6は並行しても良い。

各フェーズに「ゴール」「タスク」「完了の定義(Done)」を明記する。
着手時にこのファイルのチェックボックスを更新しながら進めること。

## Phase 1: データ生成パイプラインの実運用化

**ゴール**: `tools/data_generator.py` を実際にOverpass API / Wikipedia APIに
接続して動かし、数百〜数千件規模の地点データを生成できる状態にする。

### タスク
- [ ] 地方・都道府県単位でbboxを分割して実行するバッチ処理を実装
      (Overpassのタイムアウト・レート制限対策)
- [ ] Wikipedia API呼び出しのキャッシュ機構(同一地点の再取得を避ける)
- [ ] §5.1の孤立防止ルール(新幹線駅→主要駅→各地点の最寄り駅→ローカル線補完)を
      実データに対して機械的に適用するロジックの実装
- [ ] §7.1.1の格安flight必須ルールをOSMデータから機械的に検出・付与するロジック
      (現在は`STRAIT_ISLAND_EDGES`に手動リストとして存在。自動検出に置き換えるか、
      検出漏れがないかのバリデーションスクリプトを追加)
- [ ] 生成したJSONのスキーマ検証(必須フィールド・型・discoveryScore範囲0-100など)
- [ ] 生成データと既存の手動データ(現行31地点)を統合、または全面置き換えするかを判断
- [ ] 生成規模を小(1地方)→中(数地方)→大(全国)と段階的に拡大して動作確認

### Done の定義
- 実行コマンド一つで `data/*.json` が再生成できる
- 生成後、孤立地点(どの交通機関接続からも到達不能な地点)が0件であることを
  検証スクリプトで確認できる
- 地点数が数百件規模でもゲームがロード・プレイ可能

## Phase 2: 到達可能性判定の本実装(blockReachability.json)

**ゴール**: §7.4で仮実装した「直線距離の増減」判定を、§3.3のブロック隣接テーブル
参照に置き換える。Phase 1でデータ規模が拡大すると、直線距離ヒューリスティックの
誤判定(分岐点での往復)が増えるため、優先度は高い。

### タスク
- [ ] `data_generator.py` の Step7 (`generate_block_reachability`)を実データに対して実行
- [ ] `movement.js` の `isReachableToward(fromNode, toNode, destinationNode)` を
      blockReachability.json 参照版に差し替え(インターフェースは変更しない)
- [ ] ブロック単位の到達可能性が「実際の交通網」と整合しているか、
      デモ版で発生した往復振動ケース(例: 松山↔道後温泉、鹿児島↔那覇)で再検証
- [ ] 現行の応急処置(recentPenalty / forceUnfilteredTransport / bannedTarget)を
      残すか簡略化するかを判断(ブロック判定が正確になれば救済ロジックの出番は減るはず)

### Done の定義
- 20回以上の自動プレイテストで詰み・無限往復が発生しない
  (現行のPlaywrightスモークテストをリグレッションとして流用)
- 直線距離判定を使わずに、全ての移動候補の可否がブロックテーブルで決まる

## Phase 3: バランス調整・ゲームプレイ品質

**ゴール**: 「知らない場所を発見する」という核となる面白さが、実際のプレイ感として
成立しているかを検証し、数値を調整する。

### タスク
- [ ] 発見スコア計算式(§4)のパラメータを実データでプレイテストし、有名観光地/
      無名地点のスコア差が体感と合っているか確認・調整
- [ ] 初期所持金・交通費相場・食事/飲料コストのバランス調整
      (資金切れ→徒歩/ヒッチハイク移行が自然に起こるか)
- [ ] ランダムイベント(§7.3)の種類を拡充(現在4種類)、発生確率の調整
- [ ] ヒッチハイク成功率・格安flightの価格設定の見直し
- [ ] 空腹/喉の渇きの減衰率調整(長距離移動でも過度にペナルティが厳しくないか)
- [ ] プレイ時間の目安(1周30分〜1時間程度を想定)に合わせた全体バランス確認

### Done の定義
- 社内(自分・知人等)プレイテストを複数回実施し、致命的なバランス崩壊がない
- 「最短ルートを避けてでも寄り道したくなる」という設計意図が体感できる

## Phase 4: UI/UXポリッシュ

**ゴール**: モバイル中心の実プレイに耐えるUI品質に引き上げる。

### タスク
- [ ] 地点数増加後のマーカー密集に対応(クラスタリング or ズームレベル別表示)
- [ ] 候補カードのタップ領域・視認性の改善(モバイル実機確認)
- [ ] 地図操作(ピンチズーム・パン)と候補パネルの共存確認
- [ ] ローディング/通信エラー時のフィードバック改善
- [ ] トースト・効果演出(到着時・発見時のフィードバック強化)
- [ ] アクセシビリティ基礎対応(コントラスト比、タップ領域サイズ)

### Done の定義
- 実機(スマートフォン)で一連のプレイフローに支障がない
- 地点密集エリア(東京・大阪等)でもマーカー・候補選択が破綻しない

## Phase 5: テスト・品質保証の仕組み化

**ゴール**: 今回のデバッグで作成したPlaywrightベースのスモークテストを、
継続的に使える形で整備する。

### タスク
- [ ] 現在アドホックに書いたテストスクリプトをリポジトリ内(`tests/`等)に整理

      自動プレイテストをリグレッション化(複数シード・複数開始/目的地パターン)
- [ ] データ生成後(Phase 1後)のスキーマ・孤立検証をCIに組み込むか検討
- [ ] 主要ブラウザ(Chrome/Safari/モバイルSafari)での動作確認

### Done の定義
- `npm test` 等、単一コマンドでスモークテストが再実行できる
- データやロジックを変更した際に、詰みが再発していないかすぐ確認できる

## 推奨する着手順序の目安

```
Phase 1 (データ拡張) ─┬─> Phase 2 (到達可能性本実装) ─> Phase 3 (バランス調整)
                      │                                        │
                      └─> Phase 5 (テスト整備、Phase1と並行可)  │
                                                                 ▼
                              Phase 4 (UI/UX) ──────────> Phase 6 (公開)
                                                                 │
                                                                 ▼
                                                   Phase 7(将来拡張・任意)
```

Phase 1は最もインパクトが大きく、かつ他フェーズの前提になるため最優先。
Phase 2は「詰み・往復振動」という現デモ版で実際に発見した問題に直結するため、
Phase 1のデータ拡張後は速やかに着手すること。
